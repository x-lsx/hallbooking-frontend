# Залбук · Frontend

Vue 3 + Composition API, TypeScript strict, Vite, Vue Router 4, Pinia, TanStack Vue Query, PrimeVue 4/Aura, PrimeIcons, axios, vee-validate 4 + совместимый Zod 3. Типы генерируются из OpenAPI. Tailwind не используется.

## Запуск

Требуется Node.js 24 LTS с актуальными исправлениями и npm. Из папки `frontend`:

```powershell
npm ci
Copy-Item .env.example .env.local
npm run dev
```

Открыть http://127.0.0.1:5173. Backend должен работать на http://127.0.0.1:8000; Vite проксирует `/api`, отдельный CORS для разработки не нужен. Настройки `VITE_*` публичны: секретов в них быть не должно. Афиши не реализованы.

## Архитектура

- `src/app`: инициализация, маршруты, QueryClient, оболочка, базовые стили.
- `src/pages`: композиция экранов, без самостоятельного HTTP-кода.
- `src/features/auth`: авторизация; Pinia хранит состояние сессии, профиль остаётся в Query.
- `src/features/bookings`: календарь, форма/валидация, карточка и действия, журнал ID.
- `src/features/data.ts`: переиспользуемые запросы справочников и залов.
- `src/shared/api`: сгенерированные типы, HTTP, обновление токенов и функции API.
- `src/shared/lib`, `src/shared/ui`: чистая логика времени и общие компоненты.

Серверные данные хранятся только в TanStack Query. Ключи календаря включают зал и неделю. После действий кэш инвалидируется. При смене пользователя кэш очищается. Обновление refresh-токена объединяет параллельные запросы. Токены хранятся в sessionStorage текущей вкладки; logout удаляет локальную сессию даже при недоступном сервере. Для production желательно перейти на refresh-cookie HttpOnly — это требует изменения backend.

## Что работает

Вход/регистрация; защищённые маршруты; залы с фильтрами и серверной пагинацией; календарь недели и выбор интервала; онлайн-заявка с подразделением, форматом, количеством участников, временем и видимостью; просмотр заявки по ID; отмена автором; модерация выбранного зала с одобрением и причиной отклонения; профиль. Загрузка, пустые результаты и ошибки имеют отдельные состояния. Дизайн адаптируется к телефону.

Права модератора проверяются существующим `GET /api/rooms/{id}/moderators`: 403 означает отсутствие прав, ошибки сети не трактуются как отказ в доступе. Backend остаётся окончательной проверкой всех действий.

## Ограничения текущего API и недостающие ручки

1. **Список собственных заявок**: нужен `GET /api/bookings/my` (или эквивалент) с пагинацией и фильтрами статуса/периода. Сейчас «Мои заявки» — журнал последних 100 ID, отправленных этим браузером, отдельный для каждого пользователя; каждую запись перечитываем с сервера. Это не полная история. Сохранённые до установки фронта заявки можно открыть по ID. При очистке хранилища журнал исчезает; серверные записи сохраняются.
2. **Залы текущего модератора**: нужен `GET /api/rooms/my` либо `GET /api/user/moderated-rooms`. Пока менеджер выбирает зал из первых 100 активных залов общего каталога; доступ проверяется отдельно. Для исходных 7–8 залов этого достаточно, но для масштабирования ручка обязательна.
3. **История модерации**: календарь отдаёт только pending/approved. Нужен список заявок зала с rejected/cancelled, периодом и пагинацией; желательно включить права `can_approve/can_cancel` в детальный ответ. Сейчас отклонённую или отменённую запись можно открыть по ID, но получить полную очередь/архив нельзя.
4. **Часовой пояс корпуса**: добавить `timezone` в `BuildingResponse`. Пока используется общий `VITE_BUILDING_TIMEZONE` (по умолчанию Asia/Yekaterinburg). Для корпусов в разных поясах надо переключить утилиты на значение каждого корпуса.
5. **Редактирование профиля**: сервис/схема есть, но нет PATCH-маршрута. Требуется для пользователей с незаполненными именем/фамилией. Регистрация на фронте эти поля требует.

Рекомендуемые адреса выше — предложения, фронт не вызывает несуществующие методы. Backend не изменён. Публичные карточки скрытого события показывают только то, что разрешил сервер. Детали чужой заявки могут закономерно отдавать 404.

Регистрация ограничивает имя/фамилию 20 символами (колонки БД) и пароль 72 UTF-8 байтами (bcrypt). Это обход текущих ограничений backend на клиенте; сервер также должен согласовать свои схемы.

## Типы API

Снимок `openapi.json` получен из текущего backend, не написан вручную. После изменения backend:

```powershell
..\backend\.venv\Scripts\python.exe -B scripts/export-openapi.py
npm run api:generate
```

## Проверки

```powershell
npm test
npm run test:mutation
npm run build
```

Регрессионные проверки покрывают часовые пояса, границы рабочего времени, форму, выбор интервалов, события календаря и параллельный refresh. Stryker проверяет чистую логику времени/валидации. Реальные сценарии с PostgreSQL/Redis и доставку почты необходимо проверять с запущенным backend.

## Production

`npm run build` создаёт `dist`. Раздавать его статическим сервером с fallback на `index.html` для Vue Router. Проксировать `/api` на FastAPI. Если API на другом origin, задать `VITE_API_BASE_URL` до сборки и настроить CORS backend. Внешний шрифт необязателен: при недоступности Google Fonts используется системный стек.

## Изолированная визуальная проверка

После `npm run build` можно запустить тестовый сервер, не связанный с рабочей БД:

```powershell
..\backend\.venv\Scripts\python.exe -B tests/fixtures/preview_server.py
```

Адрес http://127.0.0.1:5174. Любые данные входа принимаются только этой тестовой средой; используйте вымышленные значения. На экране есть отметка «ТЕСТОВЫЕ ДАННЫЕ». Все изменения существуют в памяти до остановки процесса. Обычный `npm run dev` к этой среде не подключается.
